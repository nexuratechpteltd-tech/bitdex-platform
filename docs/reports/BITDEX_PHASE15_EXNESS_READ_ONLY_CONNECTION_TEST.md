## 1. Official Exness Trader API Specification

The BITDEX Exness adapter (`backend/app/services/exness/trader_api_adapter.py`) strictly complies with the official Exness Trader API specification (Ed25519 asymmetric cryptography):

### Required Security Headers
Every authenticated HTTP request to an Exness gateway requires three mandatory headers:
1. `EXN-API-KEY`: Public key string provided in Exness Personal Area Key Management (e.g. `exnsk-...`).
2. `EXN-DATA`: Unpadded Base64URL-encoded JSON string containing:
   - `api_key`: The public key string.
   - `timestamp`: Milliseconds elapsed since Unix epoch (`int(time.time() * 1000)`).
   - `body_hash`: Base64URL-encoded SHA-256 hash of the minified JSON request body (or precomputed `47DEQpj8HBSa-_TImW-5JCeuQeRkm5NMpJWZG3hSuFU` for empty GET requests).
   - `path`: Exact request path including query string (e.g. `/v1/trading/access-point?account_id=16000629657`).
   - `idempotency_key`: Optional UUID or unique string.
3. `EXN-SIGN`: Unpadded Base64URL-encoded Ed25519 signature generated by signing the ASCII bytes of `EXN-DATA` using the customer's private Ed25519 key.

### Official API Endpoints
- **DNS Gateway Discovery**: `GET /v1/trading/access-point?account_id={id}`  
  Resolves the operational cluster URL (`access_point`) and WebSocket endpoint for the specific account.
- **Account Details**: `GET /v1/accounts/{id}`  
  Retrieves account tier, currency, balance, leverage, and `is_demo` flag.
- **Account Balances**: `GET /v1/accounts/{id}/balance`  
  Retrieves cash balance, equity, margin, free margin, and margin level.
- **Open Positions**: `GET /v1/positions?account_id={id}`  
  Retrieves active contracts, volume, entry prices, and unrealized P&L.

## 3. Findings & Security Verification

1. **404 Elimination**:
   The HTTP request was received by Nginx on Port 443, correctly proxied to Port 8002, authenticated by FastAPI dependency injection, and passed to the Exness adapter. The previous `404 Not Found` error is completely resolved.

2. **Truthful Error Reporting (Zero Mocking)**:
   The backend explicitly returned `HTTP 400 Bad Request` with `status: FAILED` and `broker_authenticated: false`. The system did NOT simulate success, did NOT fabricate balances, and did NOT store a bogus "Connected" state in the database.

3. **Database Integrity**:
   Because `broker_authenticated` was `false`, `connect_exness_real` recorded `last_reconciled_at = NULL` in `exness_demo_connections`. As a consequence, `_resolve_hft_account` correctly categorizes this account as:
   ```
   Account: Exness — Real Account — #1600•••657
   Connection Status: NOT TESTED (or DISCONNECTED)
   Connected: False
   Available Balance: None
   ```

4. **Required Operational Configuration**:
   To establish a genuine live authenticated connection, the account owner must:
   - Generate an API Key in Exness Personal Area > Profile > Key Management.
   - Note the Gateway host displayed in the DNS widget.
   - Input the Gateway host and 128-hex character private key into the BITDEX Exchange Connections view.
